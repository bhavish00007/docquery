## Day 3 — The 4-Piece Upload Flow

**1. app/models/document.py**
Created the Document table — stores metadata about each uploaded file: filename, which company it belongs to (company_id), and its status (processing -> ready). This does NOT store the file itself or the extracted text, just info ABOUT the file.

**2. uploads/ folder**
A folder on disk where the actual raw PDF file gets physically saved when someone uploads it. This holds the real file, not the extracted text.

**3. app/routes/documents.py**
Created the /documents/upload endpoint. On upload it: saves the raw PDF into uploads/ -> creates a Document row (status "processing") -> extracts text from the saved PDF using pdfplumber -> updates status to "ready" -> returns a small preview of the extracted text (not stored anywhere permanent yet — that comes later with chunking + Chroma).

**4. main.py**
Wired the new documents router into the FastAPI app (same pattern as auth router yesterday) so /documents/upload is actually reachable.

**Key correction to remember**: uploads/ = raw PDF file. Extracted text = currently just shown as a preview, not saved permanently yet. Those are two different things.

## Day 4 — Chunking Confirmed Working

Result: 3 chunks created. Confirmed chunk 2 starts at word450 while chunk 1 ends at word499 — words 450-499 appear in both chunks. This overlap prevents real sentences from being cut in half at chunk boundaries, which would otherwise lose meaning during search.

## Day 4 — Chroma Vector Store

Collection: like a table in Chroma, holds all chunks.

Metadata filtering (where={"company_id": ...}): this is how tenant isolation works in the vector DB — even though all companies' chunks live in one collection, queries are filtered so you can only ever retrieve your own company's chunks.

Chroma's default embedding function: automatically converts text to embeddings when you call collection.add() or collection.query() — don't need to manually call Gemini for this step (though could swap in a different embedding model later).

PersistentClient: saves Chroma data to disk (chroma_data/ folder) so it survives server restarts.

## Embedding Model Used (Chroma default)

Model: all-MiniLM-L6-v2 — a small open-source sentence embedding model from the Sentence-Transformers family.

Where it comes from: not written by me or listed in requirements.txt by name — it's bundled inside the chromadb package itself. Since I never specified an embedding function when creating the collection, Chroma silently defaults to this model.

Where the model file lives: downloaded once and cached locally at C:\Users\<user>\.cache\chroma\onnx_models\all-MiniLM-L6-v2\ — completely separate from the project folder. Downloaded automatically the first time .add() or .query() was called, reused silently on every run after that.

What it does: converts text into a 384-number vector representing its meaning. Runs entirely locally, no internet/API call, no cost, no rate limits.

vs Gemini: Gemini is NOT used for embeddings in this project — it's reserved for Day 6 (generating the actual answer from retrieved chunks). Using local MiniLM for embeddings keeps that step free and fast, saving Gemini API quota for where it matters more — answer generation.

Could I change this? Yes — Chroma allows passing a custom embedding_function when creating the collection, which could point to Gemini's embedding API instead, for potentially higher quality at the cost of API calls and speed. Kept MiniLM for this project as a deliberate tradeoff (free, fast, good enough).

DAY 7 — deps.py

Created app/core/deps.py with a function get_current_user().

What it does: reads the JWT token sent in the request header, 
verifies it's valid (using decode_access_token from security.py), 
finds the matching User in the database, and returns that user.

Used with Depends(get_current_user) in routes (upload, query) — 
FastAPI runs this automatically before the route's own code runs.

Why: so company_id comes from the verified token, not from 
something the user could type/fake. If token is missing/invalid, 
returns 401 Unauthorized automatically.

Used HTTPBearer (not OAuth2PasswordBearer) — simpler, just needs 
the raw token pasted into Swagger's Authorize button, no 
username/password fields.
